GENERAL INFORMATION
=========================================================
=========================================================

Every tool is open source and contributions are welcome.

Special thanks to AutoHotkey user RHCP for his great classMemory.ahk, a memory reading/writing wrapper which has made my life infinitely easier https://github.com/Kalamity/classMemory

This is the frame data information I have compiled and used to decide which behaviour to use against Throws and Offensive Holds for the BusaBot (basically, the rule goes 11 frames or higher of startup = most likely an OH):
http://www.freestepdodge.com/threads/frame-data-of-all-throws.5936/

I don't use the default AutoHotkey Sleep function because this is more precise and doesn't waste CPU cycles:
DllCall("Sleep",UInt,123)
1 frame in a 60 FPS game is about 16,67 ms long but the minimum sleep I like to set is at least 20. 1000 milliseconds divided by 50 frames per second = 20, I chose to sleep longer for more input leniency, just in case of frame drops that slow down the game.

The Send commands use scan codes instead of "regular" keys for compatibility reasons. More information can be found inside combos.ahk (in a nutshell, we have to take into account that English "WASD" = "ZQSD" in a French layout).

The bot uses both WASD and Arrow Keys for movement because Arrows always have priority over WASD, which is good to override less important inputs.

The variable names I have given to the addresses + the comments should be pretty straightforward if you know a little about fighting games.

DeadOrAutohotkey (BusaBot) needs multiple AutoHotkey scripts to run at the same time because this way it is easier to make use of only specific parts of the bot. Some people do that, e.g. they only launch the auto-hold (A) part of the bot but not the rest.

BUSABOT WEAKNESSES & POSSIBLE IMPROVEMENTS
=========================================================
=========================================================

1) Imperfect move distance detection. This is because the reactions are based on the Distance between the two characters, not on hitboxes, and the Reach value of a move only shows during active frames (which is too late) so it can't be used either.
2) Doesn't react to "Combo Throw followups", in case the bot gets caught into them.
3) I couldn't find a way to distinguish a Throw from an OH with the Move Details screen closed. As a workaround, I made the bot react in a certain way against slow Throws and in another way for fast Throws because OH's tend to be slower. But maybe there's an address somewhere that I haven't found yet which may tell us if it's OH or not.
4) It doesn't Tech Roll crumple stuns and Rachel's 41236T > 8P.
5) High latency online makes the instant reactions of the bot virtually useless. Finding an address that tells me by how much an online match is currently delayed by would help a lot, but I've yet to find it. I was only able to find the frame delay values of training mode's lag simulation.

=========================================================
HOW TO FIND ADDRESSES ON CHEAT ENGINE
=========================================================
=========================================================

If you're familiar with AOB signature scans, that's what the toolbox uses from version 2.0 to auto-update its addresses. Ticking the "<- CHECK THIS PLEASE" checkbox will execute the related script.

But still, here's the older (no AOB) method I used every time to quickly update the entire Cheat Table if it stopped working after a patch:
1) open the outdated addresses.ct with the game attached
2) manually find the new P1_ComboCounter address (easiest one to find), keep it in the "Found:" list SELECTED
3) right click the old P1_ComboCounter > Recalculate new addresses > Change to address > Change
If it worked, all the addresses should be realigned. Now copy them to addresses.ahk. This should be enough to restore the correct functionality of the entire toolbox.

I will still explain how I manually found every single address I needed the first time, and discuss more details, for science.

They are all static addresses (green ones in CE), so no pointers were necessary.
But, just in case you need read the memory of a pointer, this is how it's done in AHK:
some_name := TargetProcess.read(0x01E2DF44 + TargetProcess.BaseAddress, "UInt", 0x10, 0x10, 0x0, 0x0, 0x20)

Some of these values are shared by multiple addresses. In those cases, I ignored the ones that change late and picked the ones that update sooner (you can play frame-by-frame using CE's Speedhack set at something like 0.02 to spot the small differences), and made sure they were player-side-specific, because some were not.

None of these values require the Move Details screen to be open while playing; they will still update while it's hidden. Keep in mind that the in-game Move Details display is delayed by 1 frame.

So this is how I found each. Completing Cheat Engine's "Tutorial-i386.exe" Step 2 is probably enough to learn how to find these addresses yourself:

_DESCRIPTION:	P1_Airborne
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Hidden value that updates with 1 frame of delay. The Jump Status field shown in-game is only true for Throws/OH, this one is for Strikes. When a character gets hit in the air, it will count as a Juggle.
0	= on the ground
1	= in the air
Some examples of Hayabusa moves that have some air frames in them (tested on Ver.1.10):
wr4K	= from frame 9 to frame 69
214P	= 10~19
9K	= 15~30
7K	= 15~25
9P	= 19~27
6K	= 22~36
8K	= 23~37
H+K	= 24~34
7P	= 11~18 + 1~5 (7P actually has 2 in 1 animations)
66K	= 26~32 + 1~8
236P+K	= 41~52
236P+KP	= 5~32
236P+KK	= 5~24
There's a mistake in the detection of Brad Wong 66P+K Airborne status; it's actually Airborne from frame 1, not 10 like the address displays.

_DESCRIPTION:	P1_ComboCounter
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Pretty straightforward, it's from the text that says "3-HIT COMBO!". Do a 3-hit-combo and scan 3. Do a 5-hits-combo and Next Scan 5 etc. etc. It's 0 when the opponent can move normally.

_DESCRIPTION:	P1_CurrentHealth
_VALUE TYPE:	2 Bytes
_VALUE EXPLANATION:
Default in Free Training is 300. Receive punch that does e.g. 10 damage > Next Scan "Decreased value by 10" to find it.

_DESCRIPTION:	P1_CurrentMove
_VALUE TYPE:	4 Bytes
_VALUE EXPLANATION:
This is a value that changes according to the current animation playing on your character. It's only reliable with generic/common animations and not character specific ones because those numbers are shared with other characters.
0 = idle animation (WARNING: not true for all characters such as Jann Lee who has the most complex idle animations in the game)
8803 = breakable object
8804 = breakable object back turned
8922 = rope stages wall push back turned
9152,9153 = universal sidesteps
9218 = wall bounce
9219 = wall bounce back turned
9252 = wall bounce with bigger bounce
9253 = wall bounce with bigger bounce back turned
|
Mai-specific animations:
214P+K variants	= 1330,1335
214P variants	= 1003,1081,1320,1325
236K variants	= 1004,1340,1345
236P variants	= 1310,1315

_DESCRIPTION:	P1_CurrentMoveFrame
_VALUE TYPE:	2 Bytes
_VALUE EXPLANATION:
It's a value that starts from 1 every time an animation starts and keeps increasing by 1 each frame. Good to tell the current frame of a move, this is a vital address for both the FrameCounter and the BusaBot. Also very useful to better analyse moves labelled as 0(0)0 in the Move Details window. It caps at 65535 if you stand still for about 18 minutes with the same animation.

_DESCRIPTION:	P1_Direction
_VALUE TYPE:	4 Bytes
_VALUE EXPLANATION:
0 = left side, facing right
1 = right side, facing left
65792 = right side, facing right (back turned)
65793 = left side, facing left (back turned)

_DESCRIPTION:	P1_GroundAttackAllowed
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
0 = no
1 = yes universal 8H+K/2K/2P etc. ground-hitting attacks are allowed

_DESCRIPTION:	P1_HighMidLowGround
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
1 = high attack
2 = medium attack. Some unique attacks that land in more than one position simultaneously such as Leifang's P+K and Gen Fu's 2P+K (midK+highP) are also listed as "2" 
3 = low attack
4 = ground attack
255 = some unique attacks that land in more than one position simultaneously such as Bayman's 3P+KT which is high + ground

_DESCRIPTION:	P1_LauncherHeight
_VALUE TYPE:	Float
_VALUE EXPLANATION:
Shows how high you launched your opponent. Can also be found in the Move Details page 2, but the number is rounded to just 2 decimals there.

_DESCRIPTION:	P1_MoveType
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Compared to P1_MoveTypeDetailed, this one updates 1 frame faster.
0 = movement, idle animation
2 = strikes
3 = strikes (I don't know what the difference is)
4 = inflicting throw animation
5 = whiffed holds
6 = inflicting hold animation
7 = blockstun
8 = critical stun, guard break
9 = normal hit hitstun, air juggle
10 = receiving throw animation
11 = receiving hold animation
12 = down status
13 = movement based commands with no damage such as sidesteps, attacks charging, taunts, character select poses 
14 = down-only strike (8P+K, 2P, 2K, 3P, 3K)
15 = receiving down-only strike
16 = whiffed throws, whiffed offensive holds

_DESCRIPTION:	P1_MoveTypeDetailed
_VALUE TYPE:	4 Bytes
_VALUE EXPLANATION:
^same as the above P1_MoveType, except they only apply to the startup frames for this value. Here some MoveTypeDetailed specific examples:
2 = strike startup frames
65538 = strike active frames
131074 = strike recovery frames
3 = strike startup frames
65539 = strike active frames
131075 = strike recovery frames
65541 = hold active frames
131077 = hold recovery frames
16 = throw/Offensive Hold startup frames
65552 = throw/OH active frames
131088 = throw/OH recovery frames
65536 = happens AFTER the last few frames of Mai 236P projectile for whatever reason
131072 = happens AFTER after the above explained 65536 status frames, when no buttons are pressed so it's cancellable... go figure

_DESCRIPTION:	P1_Reach
_VALUE TYPE:	Float
_VALUE EXPLANATION:
Shows the range of your attacks. Can also be found in the Move Details page 2, but the number is rounded to just 2 decimals there.

_DESCRIPTION:	P1_Stance
_VALUE TYPE:	2 Bytes
_VALUE EXPLANATION:
0 = Standing
1 = Crouching/Squatting
256 = ground
257 = ground 2 (Jann Lee's 4KKP causes it for a few frames)
512 = rolling on the floor (like when receiving Ein's 236P)
513 = rolling on the floor 2 (a few frames of Tina's 66P+K)
768 = air (like when receiving Ein's 4K)
769 = air 2 (when executing Hayabusa's headbutt 6P+K from Ongyoin or a few frames of Tina's 66P+K)

_DESCRIPTION:	P1_StrikeType
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
0 = High Punch
1 = High Kick
2 = Medium Punch
3 = Medium Kick
4 = Low Punch
5 = Low Kick
255 = not a strike (hold/throw/ground attack)

_DESCRIPTION:	P1_TotalRecovery
_VALUE TYPE:	2 Bytes
_VALUE EXPLANATION:
Can be checked from the Move Details. Value updates instantly when a move starts, not progressively. Make sure it's player-specific. There are several instances where this value is completely wrong, such as strikes that have different on hit/on whiff/on block animations (e.g. Alpha-152's 7K shows 0 recovery, and Mai's 236K shows 0 and 1), so this is not always reliable.

_DESCRIPTION:	P1_TotalStartup
_VALUE TYPE:	2 Bytes
_VALUE EXPLANATION:
Can be checked from the Move Details. Value updates instantly when a move starts, not progressively. Make sure it's player-specific. I'm only aware of 3 cases where the value is reported incorrectly: Leifang 1K (shows as 20 it's actually 17), Mai 236K (shows 1 for both hits), Akira knee (shows as 16 it's actually 18).

_DESCRIPTION:	PX_BattlePhase
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
0 = nothing/black loading?
1 = character intros + GET READY FIGHT
2 = battle
3 = KO phase
5 = battle over
7 = first time game boot?

_DESCRIPTION:	PX_Distance
_VALUE TYPE:	Float
_VALUE EXPLANATION:
Not player side specific. Can be checked from the Move Details page 2, but the number is rounded to just 2 decimals there. "Exact Value" scans are not recommended, use ranges or increases/decreases instead since it's Float type.

_DESCRIPTION:	PX_Timer
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Not player side specific. This is the Timer of a match. This is a number that starts from 0, increases by 1 every second, and resets to 0 every time it reaches the current time limit set. If the time is set to unlimited, it resets after reaching 59.

_DESCRIPTION:	PX_TotalActiveFrames
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Not player side specific, but it still works fine for what I need. Can be checked from the Move Details. Value changes instantly, not progressively. Correctly detects the active frames of holds.

_DESCRIPTION:	P1_XAxis P1_YAxis
_VALUE TYPE:	Float
_VALUE EXPLANATION:
This is the position of your character in the stage, editing this will teleport you around. This information I gathered is based on Dojo with the default spawn point:
X=horizontal Y=vertical
P1 X = -1
P1 Y = 0
P2 X = 1
P2 Y = 0
Walking up makes the Y go negative for both.

_DESCRIPTION:	PX_KOTimer (freeze me to 100)
_VALUE TYPE:	4 Bytes
_VALUE EXPLANATION:
This is the time you have to wait from one round to another while one of the characters is dead. Starts at 179 when the character(s) of one side dies and decreases by 1 every frame until it reaches 0 and the next round begins. Freeze it to something like 100 to have infinite KO time.
The "infinite timer toggle" script contains a AOB scan script that toggles the related opcode behavior from dec to inc, thus making the KO Timer infinite or not, and it works in every version.
Of all the addresses in the CT, this one seems to be the only one that stayed the same for several patches in a row for some reason.

_DESCRIPTION:	P1_SlowmoKOMovementBlock
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
Normally, ending a round with a "big" move puts the game in slow motion and stops the winner from moving. Freezing this address to 0 allows the winner to move freely.
0 = movement allowed
1 = movement disallowed

_DESCRIPTION:	COM only toggle
_VALUE TYPE:	(AOB scan)
_VALUE EXPLANATION:
Tick this script and start any offline mode match to sit and watch the AI battle each other. Also recommended to freeze all P1A_COMLevel to 7 together with it to make the matches more alive.

_DESCRIPTION:	P1A_COMLevel
_VALUE TYPE:	Byte
_VALUE EXPLANATION:
0 = COM difficulty Level 1
7 = COM difficulty Level 8
